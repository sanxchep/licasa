# Licasa 0.9.0 release notes

**Release preparation — 27 October 2026. Intended tag: `v0.9.0`.**

Licasa 0.9.0 brings safer installation and background-update handling, clearer
screen-reader controls, better desktop file dialogs and tighter coordination
between previews, full-resolution images and neighboring-photo caches. It also
includes a broad reliability and housekeeping round, with regression tests for
the failure paths behind these changes.

These notes consolidate **everything since the published
[0.8.1 release](https://github.com/sanxchep/licasa/releases/tag/v0.8.1)**, rather
than describing only the most recent cleanup commit. That includes the startup,
accessibility and AppImage dialog work merged through
[PR #5](https://github.com/sanxchep/licasa/pull/5), followed by the background
lifecycle, installation, image-loading and cleanup work in
[PR #6](https://github.com/sanxchep/licasa/pull/6). The baseline is release commit
`37181b9e6450654d3386e67edbce52f15ea8abdd`.

Version metadata and these notes prepare 0.9.0 locally. They do not mean the
tag, release assets or Snap Store channels have been published. Final source,
package and release qualification still apply.

## Highlights

- **Safer updates:** identify the affected installation, prepare an idle viewer,
  stop it normally and observe its exit before replacing the runtime.
- **Better accessibility:** fix Orca's repeated decimal-tail announcements,
  improve reset/compare actions and strengthen keyboard focus restoration.
- **Clearer startup:** opening Licasa without a photo displays the bundled
  high-resolution logo as a real image in the normal viewer.
- **Better portable dialogs:** include matching GTK and GIO components for
  desktop-integrated AppImage Open/Save dialogs, with the Qt fallback retained.
- **Less redundant image work:** preserve preview/full pairing across request
  order, reuse adequate neighbor rasters and avoid enlarging tiny cache images.
- **Stronger failure handling:** repair PNG cleanup, GPU transfer/identity
  lifetimes, unsafe log destinations and malformed update metadata.

After testing 0.8.1, the reporter raised further questions about the empty

## 2. Startup, opening images and everyday controls

Launching without a filename now opens the bundled **4096 × 4096 Licasa logo**
as an actual assigned image. It uses the ordinary image probe, decode and
rendering paths, so fit, zoom, fullscreen, editing and saving work as they do
for a photograph. There is no separate welcome panel or central startup Open
button. **Ctrl+O** opens a photo, **F11** switches fullscreen/windowed mode,
and **Ctrl+,** opens Settings.

A launch with an explicit photo goes directly to that photo without first
showing the logo. Selecting a real photo can reuse an unedited default-logo
view. If the logo has been edited, the existing new-window behavior preserves
those edits instead of replacing them.

Hidden background startup remains hidden and does not decode a default image.
Showing an empty background shell loads the logo through the normal path.
Unsupported or unreadable initial files leave a persistent retry view with a
useful Open action; loading and failure remain separate states.

Settings remains reachable from default/empty and floating-window states.
Window activation, picker cancellation, Settings closure and background
reactivation restore focus to useful controls. The displayed image has an
accessible name for the logo or selected filename, and the empty-view close
action announces its purpose.

## 3. Keyboard and screen-reader behavior

Adjustment sliders now expose readable whole-percent values to assistive
technology. This fixes the repeated-nines/long-decimal announcements without
rounding the actual adjustment settings or reducing editing precision. Tests
cover positive, negative and zero values and inspect generated Orca speech as
well as AT-SPI events.

The memory-limit setting exposes whole MiB to screen readers while preserving
its GiB visual display. The playback timeline exposes percentage progress.
Accessible names, ranges, increments, focus and increase/decrease actions
remain available.

Individual adjustment resets gain keyboard/screen-reader actions and restore
focus to a useful control. **Compare with original** exposes a checkbox toggle
action and its current state. Open, Save As, crop, adjustment, Settings and
error journeys have expanded focus and value checks.

Animated-image Play, Seek and Step now respect disabled interaction. Shared
playback admission retains active Motion Photo Pause/Seek while a still-image
promotion is waiting. Existing modal-dialog shortcut blocking remains in force,
so picker keys cannot unexpectedly activate the viewer behind a dialog.

The automated MATE/Orca checks verify concrete interaction and generated-speech
behavior. Listening on audio hardware, real desktop variations and complete
accessibility acceptance remain separate work.

## 4. AppImage Open/Save dialogs and desktop integration

Portable builds include the GTK platform-theme plugin from their **matching
Qt runtime** and its GTK dependency closure. On supported desktops this enables
native GTK Open and Save As dialogs. The launcher no longer forces a
GNOME/XFCE theme selection; Qt can detect the actual desktop, while an explicit
`QT_QPA_PLATFORMTHEME` selection remains respected.

A matching dconf settings backend is shipped in a private GIO module directory.
Scoping module lookup to the application avoids loading incompatible host GVFS
modules into the bundled GLib runtime. This improves local-file dialogs; it
does not introduce remote GVFS browsing or guarantee identical styling with
every third-party theme or portal.

The complete Qt Quick fallback and its dependency preflight remain available.
An unavailable native provider can fall back, while incomplete dialog imports
remain recoverable without discarding the current photo or edits.

Portable native/fallback journeys cover light and dark themes, spaces and
Unicode in paths, filters, cancellation, reopening, overwriting, focus and
decoding the saved output. Recovery qualification retains the installed
default-image asset when isolating the runtime.

## 5. Preview/full-image loading and browsing

### Pair requests without duplicating work

Preview/full-image registration now works regardless of which request arrives
first. Both roles claim the same bounded attempt using the source/rendering
fingerprint. A full request cannot replace a live registration and accidentally
duplicate decoding or lose its prepared counterpart.

Duplicate roles and mismatched rendering settings are rejected. Presentation
and cancellation state survive a late counterpart, and presentation uses the
identity of the attempt actually displayed. The registry holds at most
**128 pairs**; at capacity it falls back to ordinary decoding instead of
evicting a live attempt. Releasing picture resources clears the relevant scope.

Eligible still-image formats retain preview/full overlap under the existing
resource admission rules. PNG and PNM first activate the ordinary preview and
then preload full detail in the spare image slot, keeping the preview visible
during promotion. Full decoding is not held behind the presentation delay.
Cancelled or empty decoded-base results are rejected before cache publication.

### Bounded P6 previews

Eligible binary PPM/PNM **P6** files gain a streaming, area-filtered preview.
It handles fractional pixel coverage and noninteger reductions, checks
dimensions and raster byte ranges, bounds output and scratch memory, rejects
short reads and responds to cancellation. Unsupported variants use the existing
fallback. Ordinary full-detail decoding is unchanged.

### Reuse neighboring rasters at the right size

Neighbor-cache entries and active reads track the target they were prepared
for. Shrinking a window, then partially regrowing it within that coverage,
reuses adequate pixels. Growing beyond it requests a sufficiently large raster.
File identity, memory budget, cancellation and stale-result checks still apply.

Tiny neighboring images retain their native dimensions when they already fit
the target. A 1 × 1 or 2 × 2 image no longer needs an enlarged cached raster
merely because the display can scale it. Cache ownership and synchronized
metrics move into a dedicated neighbor-cache component, with shared preview
format/geometry helpers.

Directory indexing stays early, but new speculative neighbor decoding waits
until the selected ready image has produced a frame. Already prepared browse
entries remain usable while that image loads. This prioritizes the user's
selected photo without discarding useful existing cache work.

## 6. Background consent and safe shutdown

Background mode remains **opt-in and off by default**. Its consent is stored
separately from generated desktop-command text. Startup entries carry
installation ownership and schema information; foreign, customized, symlinked,
duplicate-field or unsupported entries are preserved rather than rewritten.
Recognized legacy generator forms can migrate.

Desktop command escaping covers spaces, quotes, backslashes, dollar signs,
backticks and percent signs. Tests verify actual desktop activation and
argument delivery. Stable launch paths are used instead of paths that become
invalid when an executable generation changes.

Snap stores background consent in revision-independent user-common storage,
while ordinary viewer settings remain revision-local. Explicit opt-out takes
precedence if a cooperating reverted revision restores an entry. Older,
unmodified revisions still have a manual first-upgrade/revert boundary.

A hidden Snap exits normally after a **60-second warm period** when safe.
Status probes, duplicate background launches and cancelled preparation do not
extend the deadline. Visible windows and active work prevent unsafe exit.
Desktop startup runs after login, including after reboot; no background
watchdog or automatic self-respawn is introduced.

Settings gains **Quit Licasa**, alongside **Ctrl+Shift+Q**. Explicit Quit and
termination signals follow normal cleanup. Lifecycle state accounts for visible
windows, edit/crop drafts, modal dialogs, saves, animation exports, Motion Photo
exports and pending image work. Clean visible windows may exit on explicit
Quit even when close-to-background is enabled; active work can block it.
Disabling background mode exits an idle hidden copy and removes its unmodified
owned startup entry while preserving customized entries.

## 7. Installation identity and lifecycle control

The application distinguishes a **stable installation**, an **executable
generation**, and its **working-source receipt**. User, package family and
stable installation anchor establish installation identity; Snap instance
identity survives revision changes. Co-installed formats keep distinct
ownership. A version string or process name alone does not establish identity.

The display-independent control interface runs before display, renderer, QML
and codec initialization:

```text
licasa --lifecycle identity|status|health|prepare-update|stop-for-update|cancel-update
licasa --quit
```

The newline-delimited JSON protocol bounds requests/replies to **16 KiB** and
partial-client lifetime to **two seconds**. Responses distinguish absence,
busy state, generation/identity mismatch, unsupported control, denial, timeout
and broken state. Peer credentials, PID/start identity, executable receipts and
graphical-session checks authenticate the intended target.

Preparation freezes new opens/previews and quiesces optional work. A
**30-second monotonic lease** releases preparation if its controller disappears;
the installer's separate transaction gate still protects incomplete file
replacement. A successful stop acknowledgment is followed by observing actual
process exit before mutation.

Linux startup uses a validated persistent runtime-file lock. Managed launches
take a shared gate before loading the replaceable runtime; installers take the
exclusive side. Ownership, links, ancestry and path replacement are checked,
and kernel lock ownership releases on exit/crash.

Forwarded opens are acknowledged and checked against generation and desktop
session. An identifiable idle predecessor can retire before another generation
takes over; busy or incompatible predecessors block unsafe takeover. Secondary
opens forward before initializing codecs. Startup-entry maintenance and
checksum priming defer until after initial painting, and software-renderer
retry uses the stable launcher to preserve identity and gating.

## 8. Installation, updates, removal and recovery

Closing the last window is not proof that replacing a runtime is safe. The
new adapters coordinate with the affected installation and refuse mutation
when its active work or identity cannot be verified safely.

**Before updating an older build, finish your work and fully Quit Licasa with
Ctrl+Shift+Q.** Closing a window can leave a background process running. Full
Quit is required before the first legacy Arch update or removal.

| Package family | Transaction behavior |
| --- | --- |
| Managed AppImage | Stage and inspect the replacement, take the external launch/install gate, stop a verified idle viewer, retain a durable journal/integration snapshots, and verify the installed generation. Recovery retains or restores the previous owned runtime when necessary. |
| Local deployment | Stage CMake installation before stopping the viewer, track owned/obsolete files, preserve unrelated prefix contents and restore owned files after replacement/verification failure. Desktop/login launch uses a gated launcher. |
| Ubuntu/Debian native | Prepare through incoming package handling before unpacking, then coordinate configure, remove, purge and abort paths. Keep native installation receipts and validate the replacement. |
| Fedora RPM | Coordinate scriptlets, retain file/link receipts and distinguish upgrade from final erase. |
| Arch | Ship the lifecycle helper, install script and an enforceable installed pre-transaction hook for subsequent transactions. The incoming hook cannot protect its own first legacy transaction. |
| Raw portable AppImage | Preserve portable execution without Python. Manual replacement or renaming requires prior full Quit; managed rollback does not apply to a raw file swap. |

Native gates and receipts are root-owned. Adapters validate targets and drop
credentials before per-user control. They do not launch a root GUI or execute
a user-writable helper with root privileges. A native configuration failure
keeps launch blocked while files may be mixed and requires repair/reinstall
through the package manager. **Native repair is distinct from managed rollback.**

Native packages declare Python and locking-tool dependencies. Managed AppImage
installation **and its generated launcher** require Python 3; removing Python
after installation prevents that managed launcher from working. The raw
portable AppImage retains its separate runtime requirements.

AppImage/Snap construction removes inherited native launch wrappers and
receipts before establishing the package family's own launcher/identity.
Arch publication carries `native_lifecycle.py`, `licasa.install`,
`licasa-lifecycle.hook`, `PKGBUILD` and `PKGBUILD.sources.sha256`, with the
corresponding individual checksums. Building from `PKGBUILD` requires those
matching sidecars rather than the recipe alone.

Successful replacement defers background startup to the next desktop login or
an explicit launch. Local deployment starts immediately only with `--launch`.
Update success does not promise an automatic immediate reopen.

## 9. Reliability, resource cleanup and logging

- **Malformed PNG cleanup:** keep libpng handles and owning rasters in stable
  heap state across error jumps. A truncated neighboring read can no longer
  bypass destruction of its scratch row. Decoder arithmetic and established
  retention policy remain unchanged.
- **CUDA/OpenCL failure lifetimes:** drain pending host transfers on error
  paths, including upload failure before kernel setup. Invalidate retained
  source identity before replacement and after failed execution/completion;
  publish reuse identity only after successful readback. Later edits cannot
  mistake stale device contents for the requested source.
- **Safe logging destinations:** open nonblocking, then validate ownership,
  regular-file type and a single link before permission changes/appends. FIFO
  targets cannot hang logging and hard links cannot redirect writes into
  unrelated contents. Private local logs still may contain photo paths.
- **Malformed update metadata:** validate receipt/journal object shapes and
  Local inventories. Invalid JSON/non-UTF-8 data produces controlled recovery
  guidance; failed lock acquisition closes its descriptor.
- **Truthful diagnostics:** preview and RAW-fast frames no longer count as
  full-detail readiness/presentation. Policy-limited RAW is observed for the
  full promised 250 ms and forbidden promotion is rejected throughout immediate
  and deferred policy discovery.
- **Housekeeping:** consolidate repeated startup parsing, browse completion
  and playback admission; remove obsolete Local presence/background helpers
  and unused imports. Separate cache responsibilities while retaining normal
  decoder/media teardown and direct image-slot bindings after performance
  evaluation.

## 10. Regression coverage and validation

New regressions check actual output and ownership: raster dimensions/pixels,
retained bytes, cache hits, resize growth/shrink/regrowth, budget changes and
release; malformed PNG cleanup; startup ownership; FIFO/hardlink logs; invalid
metadata; lock cleanup; disabled animation commands; editor history/reset/crop;
async image failure/recovery; and the actual Main prefetch sequence.

Test-only CUDA/OpenCL interfaces compile the production adapters without a GPU
SDK. Injected upload, execution and completion failures check queue drain,
restored pixels, invalidated receipts and released buffers. Fake driver
libraries stay isolated to tests and are never installed with the application.
Diagnostic state machines execute in controlled child processes. Preserved
older implementations fail the corresponding regression/negative-control cases.

The application qualification baseline passed:

| --- | --- |
| Ubuntu / Qt 6.4.2 full profile | 74 registered: 72 passed, two physical CUDA/OpenCL checks skipped; build and QML checks passed. |
| Debian / Qt 6.8.2 full profile | 74 registered: 72 passed, the same two hardware checks skipped; build and QML checks passed. |
| Core Release | 57 registered: 55 passed, two hardware checks skipped; build and QML checks passed. |
| Python | 356 passed, zero skips. |
| ASan/LSan/UBSan | All 11 selected suites passed with leak detection and the recorded narrow Qt software-scene-graph suppression. |
| Standards | All 178 first-party C++ files passed formatting; whitespace and public-path checks passed. |
| Process control | Normal and sanitized real-viewer lifecycle campaigns passed; emulated Snap checks exercised bounded timing. |
| Installed artifacts/desktops | Ubuntu/Debian/AppImage runtime/install checks, native GTK dialogs and virtual MATE/Orca journeys passed. |
| Update/remove journeys | Managed, RPM and Arch each passed eight actual viewer journeys; managed desktop activation passed. |

Managed journeys include legacy refusal, cooperative replacement/downgrade,
clean visible Quit, live uninstall, legacy removal after full stop, Local
overlay replacement and the deployment CLI. Native journeys include installed
receipts, environment isolation, hidden safe reinstall, visible busy refusal
without byte/process mutation, Quit, running removal, reinstall without
resurrection and concurrent startup/control.

Cooperating generations in managed tests include an inert ELF marker to
distinguish same-version executables. They prove generation handoff, rather
than an upgrade between two independently published releases. Emulated Snap,
virtual desktops and fake GPU drivers retain their respective qualification
limits.

Wayland dialog qualification now waits for actual keyboard focus before
sending its opening shortcut. Recovery requires a fresh retained picker-error
entry for each failure/retry, avoiding dependence on a toast that later image
events can replace. Isolated native recovery retains the default-image asset.
One Debian lifecycle suite exceeded its unchanged 60-second timeout during
heavy concurrent work; its failure was retained and the complete registry
subsequently passed without changing timeout or test code.

These results bind to application source receipt
`f50dfafe83f64636ceef523ca5cb6a8c1b3c887760ec32dd68917e6f37905e82`,
the source installed for local review and committed in PR #6. **The new version
and release-note inputs change the source receipt.** Existing 0.8.1-labelled
qualification packages are not renamed into qualified 0.9.0 assets, and these
local results do not stand in for completed hosted CI or final release checks.

Follow-up CI fixes run per-user lifecycle tests with real unprivileged
credentials in native builders, distinguish launcher scripts from application
binaries, and validate final package reports before returning success. The
updated Python suite passes **360 tests**, and all five local PR package-report
checks pass for the recorded test artifacts.

### Performance evidence

All **21 original maintenance gates** passed across the default image, a
Full-HD JPEG and a 100MP image. Each case used **40 paired measurements plus
two warmup pairs**, unchanged observer/runtime/plugins/fixtures and fresh
settings/QML caches. The original thresholds were retained:

- Timing p50: reference + max(3%, 5 ms).
- Timing p95: reference + max(5%, 10 ms).
- Median post-close RSS: reference + 5,120 KiB.

Selected reference → final-cleanup measurements:

| Case | First-window p50 (ms) | First-window p95 (ms) | Median post-close RSS (KiB) |
| --- | ---: | ---: | ---: |
| Default image | 351.34 → 348.88 | 382.47 → 372.86 | 66,632 → 66,688 |
| Full-HD JPEG | 152.69 → 142.75 | 174.23 → 181.16 | 67,108 → 67,148 |
| 100MP image | 446.41 → 459.64 | 504.85 → 497.37 | 67,582 → 67,708 |

The reference is the preserved **pre-cleanup working build**, which already
included lifecycle changes. This establishes the housekeeping performance
boundary; it is not a cumulative speed comparison against published 0.8.1 or
a claim that every workload became faster. Earlier failed candidates and all
samples remain retained; limits and sample counts were not relaxed.
